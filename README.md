# Smart Logistics Platform

Учебный проект: PostgreSQL (public → Core → Mart), ClickHouse, Airflow и batch inference тарифов.
Исходные сделки синтетические; фиксированная дата снимка — **2026-10-26**.

## Запуск

Заполнить `.env` по `.env.example`, затем:

```bash
docker compose up -d --build
```

В Airflow (`http://localhost:8080`) запустить **`0_slp_start`**. Он загрузит Core,
подготовит Mart PostgreSQL и ClickHouse, обновит карточки маршрутов и вызовет **`slp_ml_prices`**.
При первом запуске ML DAG обучит модель, сохранит её и запишет прогнозы в PostgreSQL.
Для повторного ML-запуска на готовом Core можно запускать только `slp_ml_prices`.
Все DAG запускаются вручную, кроме существующего ежедневного обновления цен.
Изменения таблиц описаны в SQL инициализации, отдельных миграций нет.

## ML: данные и признаки

`sql/queries/ml_prices.sql` читает Core: одна строка на `price_id`, два справочника городов,
список бизнес-групп кузова с fallback. `price_dates` не размножает ML-датасет: дата — `loading_date`.
Используются расстояние, вес, объём, их категории, отдельные регионы и координаты отправления
и назначения, флаги групп кузова, календарные признаки и циклические sin/cos.
Города исключены из baseline в пользу регионов и координат; это выбор baseline, а не запрет задания.

### Кузова и смысл прогноза

Модель оценивает одну стоимость отправки с заданным набором допустимых кузовов:
«Перевозка будет стоить примерно X рублей; выполнить её можно указанными вариантами кузова».
Отдельную ставку для каждого кузова внутри набора модель не рассчитывает.

Кузова из `core.price_body_types` приводятся к бизнес-группам через `core.body_types.std_id`.
При отсутствии связей используется `core.prices.body_type`, затем группа «Не указан».
Повторы внутри группы устраняются; одна сделка остаётся одной строкой обучения.
В признаки передаются независимые флаги 0/1: например, для тента и борта одновременно
`body_tent = 1`, `body_board = 1`, остальные флаги равны 0.
Основной `prices.body_type` отдельным признаком не используется.

В `mart.ml_price_predictions.body_group_ids` сохраняется весь набор, например `[15, 56]`,
и один прогноз для отправки. Различные наборы кузовов могут давать разные прогнозы.
В проверенном снимке встречаются пары «Изотерм + Рефрижератор», «Борт + Тент»
и «Прочие + Тент». Это свойство текущей синтетики, а не ограничение допустимых сочетаний в коде.

### Отбор данных и временные выборки

Таргет — `price_rub`, RUB без НДС. В признаки не входят цена, её производные,
ценовые агрегаты, идентификатор сделки и флаги постфактум. `outlier_mark` используется
только для отбора исторической выборки. Любые обучаемые преобразования должны обучаться на train.

Фильтры истории: фактические прямые перевозки (`price_type IN (1,2,3,4,5,9)`),
без отмеченных выбросов, конечные положительные таргет и расстояние,
конечные неотрицательные вес и объём. Будущим заявкам не требуются известный таргет,
`is_fact` или `outlier_mark`; прямой маршрут и валидные входные параметры сохраняются.
Core уже применяет DQ: строки без валидной цены или курса в него не попадают.
Все ML-выборки, включая будущий скоринг, формируются исключительно из Core.
Если нужны дополнительные данные RAW, сначала их нужно загрузить в Core отдельным ETL.
В текущем снимке для скоринга после фильтров доступны 5820 будущих заявок.


- Train: `[2026-07-26, 2026-10-05)`.
- Test: `[2026-10-05, 2026-10-26]`.
- Future: `loading_date > 2026-10-26`.

Последние 14 дней train — внутренняя validation для early stopping. Затем CatBoost обучается
на всём train с выбранным числом деревьев. Test не используется для выбора параметров.
Seed=42, CPU, 4 потока, depth=6, learning_rate=0.05, максимум 1500 деревьев, patience=100.
Метрики train/test: R², RMSE и MAE в рублях, MAPE в процентах; baseline — средний тариф train.
Референсы R&D не являются обязательными порогами качества.

В notebook получены test R²≈0.922, RMSE≈53581, MAE≈27703, MAPE≈15.4%.
Это оценка синтетического генератора. Короткий train не покрывает полный год сезонности;
неразмеченные выбросы могут ухудшать метрики. Качество на реальном рынке не подтверждено.
Эксперименты и SHAP остаются в локальном `sandbox/ml_prices.ipynb` (каталог игнорируется Git).

## Сохранение и скоринг

Модули `slp/ml/`: `data.py` — чтение, `features.py` — отбор и признаки,
`training.py` — обучение и артефакты, `pipeline.py` — публикация и задачи Airflow.

`artifacts/ml/<model_version>/` содержит:

- `model.cbm` — обученные деревья CatBoost;
- `manifest.json` — параметры, признаки, метрики, версии библиотек, контрольные суммы;
- `scoring_input.json.gz` — снимок test/future для согласованного скоринга.

В WSL это локальный `artifacts/ml/` (игнорируется Git). В Docker каталог
`/opt/airflow/artifacts/ml/` хранится в общем именованном volume `ml_artifacts`.
Он создаётся с правами записи Airflow автоматически, даже на чистом клоне. Модель создаётся при выполнении DAG,
а не при сборке образа. Версия определяется данными, параметрами, кодом и версиями библиотек.
Повторный запуск с тем же снимком повторно использует проверенные артефакты.
Повреждение файла приводит к явной ошибке проверки, а не скрытому скорингу.

`mart.ml_models` хранит метаданные и относительный путь к файлу.
`mart.ml_price_predictions` хранит прогнозы test и future; ключ — `(price_id, model_version, as_of)`.
Будущие `actual_price_rub`, `abs_error_rub`, `ape_pct` всегда NULL, даже если генератор знает цену.
Сравнение с синтетическими будущими ценами оставлено только в notebook.
Публикация версии атомарна; повторный скоринг не создаёт дублей. Старые версии сохраняются.
Таблицы создаются SQL инициализации; для существующего volume DAG применяет тот же DDL при отсутствии.

```sql
SELECT prediction_set, count(*)
FROM mart.ml_price_predictions
GROUP BY prediction_set;

SELECT model_version, metrics FROM mart.ml_models ORDER BY trained_at DESC;
```

## Проверки

```bash
uv run pytest
uv run ruff check slp/ml tests/test_ml_pipeline.py dags/slp_ml_prices.py
```

Без флагов интеграционные тесты пропускаются. Для них нужны заполненные настройки
подключений и `SLP_RUN_DB_TESTS=1`; для ClickHouse также `SLP_RUN_CH_TESTS=1`.
ML-тесты проверяют границы дат, отсутствие таргета в X, несколько кузовов,
загрузку модели, скрытие будущего факта, контрольные суммы, повторную публикацию
и откат после ошибки записи. Тесты БД откатывают свои изменения.
