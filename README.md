# Smart Logistics Platform

Учебный проект: PostgreSQL (public → Core → Mart), ClickHouse, Airflow и batch inference тарифов.
Исходные сделки синтетические; фиксированная дата снимка — **2026-10-26**.

## Запуск

Скопировать пример настроек в `.env`:

```bash
cp .env.example .env
```

Заполнить пароли и `AIRFLOW_JWT_SECRET` в `.env`, затем запустить проект:

```bash
docker compose up -d --build
```

В [Airflow](http://localhost:8080) вручную запустить **`init`** — стартовый конвейер
создаётся без паузы и без расписания.

При запуске будут загружены справочники, а сырые данные пройдут проверку качества,
очистку, пересчёт валютных цен в рубли и заполнение недостающих категорий.
Невалидные записи попадут в карантин с указанием причин. Подготовленные данные
будут идемпотентно загружены в Core: повторный запуск не создаёт дублей,
а изменившиеся записи обновляются.

На основе Core будут построены подготовленные аналитические данные в PostgreSQL,
синхронизированы месячные партиции ClickHouse и обновлены карточки маршрутов
с коридорами рыночных ставок в обеих СУБД.

При первом запуске будет обучена и сохранена модель прогнозирования тарифов,
а прогнозы для тестового и будущего периодов будут записаны в PostgreSQL.
При неизменных данных и настройках повторный запуск использует сохранённую модель.
Обучение и скоринг также можно запустить отдельно вручную после подготовки Core.

Дальнейшее обновление справочников, Core и аналитических витрин выполняется ежедневно
по расписанию с 09:00 до 10:15 по Москве (Europe/Moscow). Переобучение модели
по расписанию не выполняется.

Структура таблиц задаётся SQL-скриптами инициализации; отдельные миграции не используются.

## Архитектурные решения

PostgreSQL 17 хранит все три слоя в одной базе: RAW в схеме `public` — синтетические
данные из задания, Core в схеме `core` — очищенные и обогащённые данные, Mart в схеме
`mart` — аналитические витрины и результаты ML. Там же хранится служебное состояние
пайплайнов. RAW логически рассматривается как внешний источник: данные из него
переносятся в Core через Python ETL. Обновление данных PostgreSQL выполняется транзакционно.
ClickHouse — бонусная реализация тех же аналитических данных на MergeTree,
с заменой месячных партиций вместо фоновой дедупликации. Airflow задаёт зависимости,
повторы и наблюдаемость задач. CatBoost выбран для прогнозирования стоимости перевозки: он умеет работать
с числовыми параметрами и названиями регионов без дополнительного преобразования этих названий.

## Core

В схему `core` через Python ETL перенесены необходимые таблицы RAW.
Сначала загружаются три справочника — они могут выполняться параллельно.
После них загружаются цены, затем параллельно даты сделок и связи с кузовами.

| Порядок | Таблица | Что хранится и как загружается |
|---|---|---|
| 1 | `core.cities` | Справочник городов. Источник читается полностью; дубли по `gc_id` устраняются выбором строки с минимальным `id`. Загрузка через UPSERT по `gc_id`: существующие города обновляются, повторный запуск не создаёт дублей. |
| 1 | `core.body_types` | Справочник кузовов и соответствий стандартным группам через `std_id`. Читается полностью и загружается по `id`. Сначала создаются строки, затем обновляются ссылки на стандартные типы. Повторный запуск не создаёт дублей. |
| 1 | `core.exchange_rates` | Курсы валют. Источник читается полностью, проверяются код валюты и положительное значение курса. При дублях на код и дату выбирается запись с максимальным `id`. UPSERT по `(num_code, setting_date)` обновляет курс без создания дублей. |
| 2 | `core.prices` | Очищенные сделки. Источник читается пакетами за окно изменений по `COALESCE(updated_at, created_at)`. Проверяются цена, расстояние, груз и наличие городов; цена пересчитывается в RUB по точному курсу на `nearest_rate_date`, заполняются отсутствующие категории. UPSERT по `id` обновляет изменившиеся данные, пропускает неизменённые и не позволяет старой записи затереть новую. |
| 3 | `core.price_dates` | Даты сделок для последующей развёртки по месяцам. Полный снимок RAW передаётся через Python во staging; наборы изменившихся связей атомарно заменяются. Обрабатываются добавления, изменения и удаления, повтор неизменного снимка не меняет данные. |
| 3 | `core.price_body_types` | Связи сделок с допустимыми кузовами. Загружаются аналогично датам: полный снимок, сравнение с Core и атомарная замена изменившихся наборов связей без дублей. |

У трёх справочников полное чтение источника сочетается с UPSERT: исчезнувшие из RAW
строки автоматически не удаляются. У двух таблиц связей выполняется синхронизация
полного снимка, включая удаления.

Флаг `outlier_mark` сохраняется в Core без пересчёта. Сам по себе он не исключает
сделку из Core: фильтрация выбросов применяется при подготовке рыночной выборки и ML.

Таблицы RAW `favorite_directions`, `selected_directions`, `migrations`,
`price_participants` и `price_group_stats` сохраняются как часть исходной схемы,
но не читаются нашим ETL, расчётами витрин и ML: для выполнения задания они не требуются.
Показатели `price_group_stats` дополнительно запрещены в признаках модели,
поскольку могут включать цену предсказываемой сделки и приводить к утечке данных.

## DQ: карантин невалидных цен

В схеме `dq` при инициализации PostgreSQL создаётся пустая таблица
`dq.quarantine_prices`. Она заполняется во время загрузки `prices`:
вместо попадания в Core невалидная запись регистрируется с `price_id`, датой погрузки,
кодом причины и временем обработки. Например: некорректная цена, отрицательный вес,
отсутствующий город или недоступный валютный курс.

Ключ `(price_id, reason_code)` не позволяет повторному запуску дублировать одну ошибку.
У сделки может быть несколько причин отбраковки. Если данные исправлены, ошибка
помечается как решённая (`is_resolved`, `resolved_at`), а история сохраняется.
Если уже загруженная сделка стала невалидной, она удаляется из Core,
а изменение регистрируется для пересборки зависимых данных Mart.

## Mart: подготовленные данные и результаты ML

Таблицы аналитического слоя создаются SQL-скриптами инициализации и заполняются пайплайнами.

| Таблица | Назначение и обновление |
|---|---|
| PostgreSQL: `mart.prices_prepared` | Подготовленные цены с ключом `(price_id, month, body_group_id)`. Месяцы берутся из `core.price_dates`, кузова приводятся к бизнес-группам без повторов внутри группы. При отсутствии связей используется кузов из сделки, затем «Не указан». Сохраняются будущие месяцы и исходные флаги. Первый запуск полный; последующие обрабатывают изменившиеся сделки. |
| ClickHouse: `prices_prepared` | Копия подготовленных данных PG на MergeTree с месячными партициями. Для каждого затронутого месяца все актуальные строки читаются из PG, загружаются в `prices_prepared_stage`, затем готовая партиция заменяет старую. Если месяц опустел, его партиция удаляется. Повторная загрузка не создаёт дублей. |
| PostgreSQL: `mart.ml_models` | Реестр моделей: версия, параметры, признаки, метрики, дата обучения и путь к сохранённому файлу модели. Одна запись на версию; обученная модель хранится отдельно от БД. |
| PostgreSQL: `mart.ml_price_predictions` | Прогнозы стоимости отправок для test и future. Одна строка на `(price_id, model_version, as_of)`. Для test сохраняются факт и ошибки; для future они равны NULL. Повторный скоринг атомарно заменяет результаты версии без дублей. |

## Материализованные представления: карточки маршрутов

Карточка маршрута и коридор рыночных ставок реализованы в двух СУБД:

- PostgreSQL: `mart.mart_route_card` — материализованное представление,
  создаваемое без данных и наполняемое командой `REFRESH MATERIALIZED VIEW`.
- ClickHouse: `mart_route_card` — refreshable materialized view на MergeTree.
  Пересчёт запускается явно из Airflow; собственное периодическое обновление CH остановлено.

Обе карточки полностью пересчитываются после подготовки данных PG и синхронизации CH.
Обычный SELECT читает сохранённый результат и не запускает расчёт заново.

Гранулярность: **месяц × город отправления × город назначения × группа кузова × весовая категория**.
В расчёт входят только фактические прямые перевозки с положительной ценой и расстоянием,
рассчитанной ценой в RUB и без `outlier_mark`. Даты из `price_dates` после `2026-10-26`
исключаются из исторической выборки; для точного ограничения внутри месяца используется
`first_price_date` подготовленной таблицы.

Показатели карточки:

- P25, медиана, P75 и средняя цена за рейс; P25, медиана и P75 цены за километр.
  Цена за километр рассчитывается для каждой сделки до вычисления квартилей.
- `trips_count` — число уникальных сделок в ячейке.
- `carriers_count` — число уникальных организаций-перевозчиков в ячейке:
  `COUNT(DISTINCT organization_id)` только для `price_type IN (3,9)`.
- `cv_rate` — разброс цен относительно среднего; при одном наблюдении возвращается NULL.
- MoM/YoY — изменение медианы к календарному предыдущему месяцу и тому же месяцу прошлого года.
  Если соответствующей ячейки нет, результат NULL.
- `reliability_level` — HIGH при минимум 30 сделках, 5 перевозчиках и свежести не более 30 дней;
  MEDIUM при минимум 10 сделках; иначе LOW_DATA.

`freshness_days` — возраст календарного месяца ячейки: от конца месяца до `as_of`,
а для текущего месяца — 0. Это не возраст последней фактической перевозки.

## Служебное состояние пайплайнов

В схеме `meta_data` находятся:

- `changed_prices` — журнал изменений цен и связей Core;
- `mart_checkpoint` — последнее обработанное событие для каждого потребителя;
- `mart_changed_months` — старые и новые месяцы, затронутые обновлением PG Mart.

PG Mart обрабатывает журнал от checkpoint, пересобирает изменившиеся сделки и фиксирует
затронутые месяцы. CH затем перечитывает эти месяцы целиком из PG.
В PG изменения данных и соответствующего состояния фиксируются в одной транзакции.
В CH партиции публикуются по отдельности, а checkpoint сохраняется после обработки всех месяцев;
при сбое повторный запуск повторяет замену без дублей.
Изменение самих справочников городов или маппинга кузовов не регистрируется в журнале:
в этом случае нужен полный пересчёт PG Mart (`mode=full`), синхронизация CH и обновление карточек.
Для фиксированного снимка справочники неизменны.

## Оркестрация

Первоначальная загрузка запускается вручную через `init`. Он выполняет дочерние DAG
в указанном порядке и ждёт их успешного завершения перед переходом к следующему этапу.
Ежедневные запуски выполняются по расписанию, без датчиков ожидания.
Все времена указаны по Москве (Europe/Moscow).

| Этап | DAG | Расписание | Что делает |
|---|---|---|---|
| Старт | `init` | Вручную | Запускает всю цепочку подготовки данных, витрин и ML. |
| 1, параллельно | `load_cities` | Ежедневно, 09:00 | Загружает и дедуплицирует справочник городов в Core. |
| 1, параллельно | `load_body_types` | Ежедневно, 09:00 | Загружает справочник кузовов и соответствия стандартным группам. |
| 1, параллельно | `load_exchange_rates` | Ежедневно, 09:00 | Загружает валютные курсы в Core. |
| 2, после справочников | `load_prices` | Ежедневно, 09:15 | Проверяет и очищает цены, пересчитывает их в RUB, заполняет категории и загружает в Core. Невалидные записи направляет в карантин. |
| 3, параллельно после цен | `load_price_dates` | Ежедневно, 09:30 | Синхронизирует даты сделок. |
| 3, параллельно после цен | `load_price_body_types` | Ежедневно, 09:30 | Синхронизирует связи сделок с кузовами. |
| 4, после обеих таблиц связей | `load_prices_prepared` | Ежедневно, 09:45 | Собирает или обновляет подготовленные данные Mart в PostgreSQL. |
| 5, после PG Mart | `prices_prepared_ch_cync` | Ежедневно, 10:00 | Переносит данные в ClickHouse с заменой затронутых месячных партиций. |
| 6, после переноса в CH | `refresh_route_cards` | Ежедневно, 10:15 | Параллельно обновляет карточки маршрутов в PostgreSQL и ClickHouse. |
| Отдельная ветка после обеих таблиц связей | `slp_ml_prices` | Через `init` или вручную | Обучает либо использует сохранённую модель, рассчитывает прогнозы и записывает их в PostgreSQL. |

В `init` ветка ML выполняется параллельно с подготовкой Mart: готовые карточки для модели
не требуются. Регулярная загрузка цен читает изменения за завершившиеся сутки между
09:15 предыдущего и текущего дня.

Данные записываются идемпотентно: повторный запуск на тех же исходных данных не создаёт
дублей. Изменившиеся записи обновляются, затронутые партиции заменяются, а прогнозы
сохраняются без повторов для одной версии модели.

## ML: данные и признаки

Модель CatBoost предсказывает **стоимость одной отправки в рублях без НДС**
(`price_rub`). Прогноз учитывает маршрут, груз, допустимые кузова и дату погрузки.
Все данные для обучения, проверки и будущих прогнозов берутся только из Core.

Для каждой сделки формируется одна строка со следующими признаками:

- расстояние, вес и объём груза, весовая и объёмная категории;
- регионы отправления и назначения, координаты обоих городов;
- допустимые бизнес-группы кузовов;
- год, месяц, день недели и день года из `loading_date`, а также sin/cos-признаки,
  сохраняющие близость соседних дат на границах недели, месяца и года.

Названия городов в первом варианте модели заменены регионами и координатами,
чтобы объединить редкие направления. Кузова приводятся к стандартным группам;
для каждой группы передаётся флаг 0/1. Например, набор `[15, 56]` означает,
что перевозка допускает борт и тент. Модель выдаёт **одну цену отправки с этим набором**,
а не отдельную ставку для каждого кузова. Сделки по кузовам не размножаются.

Из исторической выборки исключаются нефактические и составные перевозки,
отмеченные выбросы, некорректные значения цены, расстояния и параметров груза.
Цена самой сделки, её производные и ценовые агрегаты не передаются модели как признаки.
Для будущего прогноза известная цена, факт завершения и разметка выбросов не требуются;
проверяются входные параметры и сохраняется ограничение на прямой маршрут.

### Обучение и оценка

Дата снимка фиксирована заданием: **2026-10-26**, независимо от даты запуска проекта.
Выборки разделяются по `loading_date`, без случайного перемешивания:

| Выборка | Период | Назначение |
|---|---|---|
| Train | С 2026-07-26 включительно до 2026-10-05 не включительно | Обучение модели. |
| Test | С 2026-10-05 по 2026-10-26 включительно | Проверка прогноза по известной цене. |
| Future | После 2026-10-26 | Прогноз для будущих заявок. |

Последние 14 дней train используются для выбора числа деревьев.
После этого итоговая модель обучается на всём train. Test не используется
для выбора параметров или остановки обучения.

**Особенность 2026-10-26:** самые свежие записи ещё не прошли ночную разметку выбросов
и могут иметь `outlier_mark = false`, даже если цена аномальная. В генераторе это записи
с `created_at >= '2026-10-26 02:30:00'`. День погрузки **2026-10-26 входит в test,
но не входит в train**: его неразмеченные выбросы не участвуют в обучении и выборе
параметров модели. Они могут повлиять на итоговые метрики test, поэтому этот день
не удаляется, а рассматривается с указанным ограничением.

На текущем синтетическом снимке после фильтров: 24 226 строк train,
12 808 строк test и 5 820 будущих заявок. Качество на test:

| Метрика | Результат |
|---|---:|
| R² | 0,922 |
| RMSE | 53 581 руб. |
| MAE | 27 703 руб. |
| MAPE | 15,41% |

Метрики также рассчитываются на train для проверки переобучения и сравниваются
с простым прогнозом средней цены train. Фиксируются seed=42 и параметры обучения:
глубина 6, скорость обучения 0,05, до 1500 деревьев, остановка после 100 итераций
без улучшения на внутренней проверке, CPU и 4 потока.

Это результат на синтетических данных, а не подтверждение качества на реальном рынке.
Короткий период обучения не покрывает полный год сезонности.

## Сохранение и скоринг

При первом запуске пайплайн обучает модель, считает метрики и сохраняет результат
в Docker volume `ml_artifacts`. Файл модели не коммитится: он создаётся при выполнении
пайплайна после развёртывания проекта.

Для каждой версии в `/opt/airflow/artifacts/ml/<model_version>/` сохраняются:

| Файл | Что хранит |
|---|---|
| `model.cbm` | Обученные деревья CatBoost, позволяющие получать прогнозы без повторного обучения. |
| `manifest.json` | Параметры, список признаков, метрики, версии библиотек и контрольные суммы файлов. |
| `scoring_input.json.gz` | Снимок test и future, чтобы скоринг использовал те же входные данные, что были подготовлены для этой версии. |

При локальных экспериментах файлы сохраняются в `artifacts/ml/`, который игнорируется Git.
Версия определяется хешем данных всех трёх выборок, параметров, кода и версий библиотек.
Если они не изменились, пайплайн проверяет сохранённые файлы и повторно использует модель.
При изменениях создаётся новая версия. Повреждённые файлы или несовместимый код признаков
приводят к ошибке проверки.

После сохранения модель загружается для **batch-скоринга**: прогноз сразу рассчитывается
для всех подходящих сделок test и future. Результаты записываются в PostgreSQL:

- `mart.ml_models` — сведения о версии, параметрах, метриках и расположении файла модели;
- `mart.ml_price_predictions` — сделка, маршрут, дата погрузки, набор допустимых кузовов,
  прогноз, версия модели и время расчёта.

Для test рядом с прогнозом сохраняются фактическая цена, абсолютная ошибка в рублях
и ошибка в процентах. Для future поля `actual_price_rub`, `abs_error_rub` и `ape_pct`
всегда равны NULL, даже если синтетический источник содержит цену.

Повторный скоринг атомарно заменяет результаты той же версии и не создаёт дублей.
Старые версии моделей и их прогнозы сохраняются. Вся цепочка выполняется из Airflow;
ручное обучение и выполнение SQL для запуска проекта не требуются.

## Проверки

Для запуска тестов и линтера на хосте нужен `uv`. Он не требуется для развёртывания
проекта через Docker Compose. Если команда `uv` не найдена, установить его в терминале
WSL/Linux по [официальной инструкции](https://docs.astral.sh/uv/getting-started/installation/):

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
uv --version
```

Изменение PATH позволяет использовать `uv` сразу в текущем терминале.
При первом `uv run` окружение `.venv` и зависимости проекта будут подготовлены автоматически.

**Запускать проверки только при поднятых контейнерах PostgreSQL и ClickHouse
и после успешного завершения `init`.** Часть тестов использует загруженные данные Core и Mart.
Команды выполняются из корня проекта.

В проекте 11 автотестов:

| Область | Что проверяется |
|---|---|
| Core | Повторная загрузка без лишнего обновления, применение свежих изменений и защита от перезаписи устаревшей записью. |
| PG Mart | Полная и инкрементальная загрузка, добавление и удаление сделок, перенос между месяцами, журнал изменений и откат при ошибке. |
| ClickHouse | Замена и удаление партиций, отсутствие дублей и корректный повтор после частичного сбоя. |
| Карточки маршрутов | Фильтры, квартили, число сделок и перевозчиков, CV, календарные MoM/YoY, надёжность и совпадение результатов PG/CH. |
| ML | Временные границы, подготовка признаков без зависимости от таргета, работа с кузовами и категориями, сохранение и версии модели, скрытие будущего факта, запись прогнозов без дублей и откат при ошибке. |
| Чистая инициализация | Доступ приложения к ML-таблицам, созданным администратором БД. |

Запуск **всех тестов**, включая проверки PostgreSQL и ClickHouse:

```bash
uv run --env-file .env bash -c '
  export SLP_CORE_DB_HOST=127.0.0.1
  export SLP_DB_PORT=5433
  export SLP_DB_NAME="$POSTGRES_DB"
  export SLP_CH_HOST=127.0.0.1
  export SLP_CH_PORT=8123
  export SLP_RUN_DB_TESTS=1
  export SLP_RUN_CH_TESTS=1
  exec python -m pytest -v -rs
'
```

Команда загружает настройки из `.env`, использует опубликованные порты контейнеров
и включает все интеграционные проверки. Ожидаемый результат — **11 passed**, без `skipped`.
Изменения тестовых данных PostgreSQL откатываются; отдельные тестовые таблицы ClickHouse
удаляются после проверки.

Дополнительно можно проверить код ML и стартовых DAG линтером:

```bash
uv run ruff check slp/ml tests/test_ml_pipeline.py dags/init.py dags/refresh_route_cards.py
```
